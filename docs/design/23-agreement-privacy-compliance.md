### 0.1 数据使用场景梳理

```
平台采集的数据可用于以下场景(需在协议中明确告知):

  ┌─── 已明确的场景 ─────────────────────────────────────────────┐
  │                                                               │
  │  1. 平台算法训练                                               │
  │     · 排产算法优化(基于历史排产数据训练更优的调度策略)           │
  │     · MRP预测优化(基于历史需求数据优化需求预测)                 │
  │     · 套料算法改进(基于历史套料方案提升利用率)                  │
  │     · 成材率预测(基于历史报工数据预测成材率)                    │
  │                                                               │
  │  2. 区域加工指数                                               │
  │     · 发布区域钢材加工产能利用率指数                            │
  │     · 发布区域品类生产趋势(管材/板材/型材占比)                  │
  │     · 发布区域材质/规格需求热度排名                             │
  │     · 所有指数数据均为脱敏聚合, 不可反推到单个企业               │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘

  ┌─── 建议新增的场景 ───────────────────────────────────────────┐
  │                                                               │
  │  3. 行业基准对标 (Benchmarking)                                │
  │     · 企业成材率 vs 行业平均成材率(同品类对比)                  │
  │     · 企业产能利用率 vs 行业平均(同规模对比)                    │
  │     · 企业换模效率 vs 行业最佳实践                              │
  │     · 帮助企业发现改进空间(匿名化对比, 不暴露具体企业)          │
  │                                                               │
  │  4. 供需匹配服务                                               │
  │     · 基于多企业的需求和产能数据, 实现加工委外撮合              │
  │     · A企业产能空闲 + B企业需求溢出 → 平台撮合加工委外          │
  │     · 需企业单独授权(opt-in), 默认不开启                       │
  │                                                               │
  │  5. 原料行情分析                                               │
  │     · 基于多企业采购数据聚合, 提供区域原料价格趋势              │
  │     · 基于库存数据聚合, 提供区域库存水位指标                    │
  │     · 脱敏聚合, 最少5家企业数据才生成指数                      │
  │                                                               │
  │  6. 产品功能改进                                               │
  │     · 基于用户行为数据优化产品UI/UX                            │
  │     · 基于操作路径数据简化操作流程                              │
  │     · 基于性能数据优化系统架构                                  │
  │                                                               │
  │  7. 客户成功服务                                               │
  │     · 基于使用数据主动发现客户使用问题                          │
  │     · 基于功能采纳率提供针对性培训建议                          │
  │     · 基于效率数据提供优化方案建议                              │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘
```

### 0.2 授权层级设计——谁来授权？

```
核心问题:
  数据以企业为单位 → 授权也应以企业为单位
  但企业里有老板、计划员、车间工人 → 谁有权代表企业授权?
  每个用户都弹窗确认 → 太烦, 且普通工人无权决定企业数据策略
  只让老板一人确认 → 老板可能不操作系统, 错过确认

设计方案: 三级授权体系

  ┌─────────────────────────────────────────────────────────────────┐
  │                    三级授权体系                                   │
  │                                                                 │
  │  第1级: 企业管理员授权 (必须)                                     │
  │  ─────────────────────                                          │
  │  · 企业开通账号时, 企业管理员(通常是老板/IT负责人)签署:            │
  │    ① 《平台服务协议》— 使用条款                                  │
  │    ② 《数据处理协议》— 数据使用范围与权限                        │
  │  · 管理员授权后, 该企业下所有用户默认遵守                        │
  │  · 管理员可在"企业设置"中随时查看/调整数据授权范围                │
  │                                                                 │
  │  第2级: 普通用户确认 (简化)                                      │
  │  ─────────────────────                                          │
  │  · 普通用户首次登录时, 展示简化版隐私告知(非完整协议)             │
  │  · 告知内容: "贵企业管理员已授权平台处理业务数据,                 │
  │              您的操作行为数据将用于产品改进。"                    │
  │  · 用户勾选"我已知悉"即可使用(不是授权, 是知悉)                  │
  │  · 若不同意 → 提示联系企业管理员                                │
  │                                                                 │
  │  第3级: 敏感功能单独授权 (按需)                                   │
  │  ─────────────────────                                          │
  │  · 供需匹配服务: 需企业管理员单独开启(opt-in)                     │
  │  · 行业基准对标: 需企业管理员单独确认                            │
  │  · 这些功能默认关闭, 授权后才开启                                │
  │                                                                 │
  └─────────────────────────────────────────────────────────────────┘

  为什么这样设计:
  · 法律上: 企业数据的处理权由企业决定, 不是由个人员工决定
  · 实操上: 管理员一人签署, 全员无需重复操作
  · 合规上: 个人行为数据告知到个人(知悉权), 企业数据由企业授权
  · 灵活性: 敏感功能单独授权, 降低一揽子授权的法律风险
```

## 1. 协议体系设计

### 1.1 协议文档结构

```
AiAPS 协议体系:

  ├── 《AiAPS 平台服务协议》 (用户协议)
  │    签署人: 企业管理员
  │    内容: 服务范围/账号管理/知识产权/免责/违约
  │
  ├── 《AiAPS 数据处理协议》 (隐私协议核心)
  │    签署人: 企业管理员
  │    内容: 数据分类/采集范围/使用目的/共享规则/安全措施/企业权利
  │    附录: 数据使用授权清单(逐项可勾选)
  │
  ├── 《AiAPS 隐私告知书》 (个人用户告知)
  │    阅读人: 每个登录用户
  │    内容: 简化版, 告知行为数据采集范围和用途
  │    操作: 勾选"我已知悉"
  │
  └── 《增值服务授权书》 (可选, 按需签署)
       签署人: 企业管理员
       内容: 供需匹配/行业基准 等增值功能的单独授权
```

### 1.2 数据分类与授权矩阵

```
┌──────────────────┬──────────────┬──────────────┬──────────────────┐
│ 数据类别          │ 示例          │ 授权方式      │ 使用范围限制      │
├──────────────────┼──────────────┼──────────────┼──────────────────┤
│ A类: 业务数据     │ 排产计划/库存 │ 企业管理员    │ 算法训练(脱敏)    │
│ (企业核心)        │ /BOM/成材率  │ 《数据处理协议》│ 不可单独识别企业  │
├──────────────────┼──────────────┼──────────────┼──────────────────┤
│ B类: 行为数据     │ 页面访问/按钮 │ 用户知悉 +    │ 产品改进/功能优化 │
│ (用户操作)        │ 点击/停留时长 │ 企业管理员授权 │ 不含业务数据内容  │
├──────────────────┼──────────────┼──────────────┼──────────────────┤
│ C类: 聚合数据     │ 行业指数/区域 │ 企业管理员    │ 对外发布(匿名聚合)│
│ (脱敏后)          │ 趋势/基准对标 │ 《数据处理协议》│ ≥5家企业才聚合   │
├──────────────────┼──────────────┼──────────────┼──────────────────┤
│ D类: 敏感业务数据  │ 客户信息/合同 │ 企业管理员    │ 仅限本企业使用    │
│                  │ 金额/供应商   │ 单独授权      │ 不参与任何聚合    │
├──────────────────┼──────────────┼──────────────┼──────────────────┤
│ E类: 系统数据     │ 性能日志/错误 │ 无需授权      │ 系统运维必需      │
│ (技术运维)        │ 日志/IP地址   │ (运维必需)    │ 不含业务含义      │
└──────────────────┴──────────────┴──────────────┴──────────────────┘
```

## 2. 协议版本管理与OSS存档

### 2.1 数据模型

```sql
-- 协议版本管理
CREATE TABLE sys_agreement_version (
    version_id          BIGINT IDENTITY(1,1) PRIMARY KEY,
    agreement_type      VARCHAR(30)   NOT NULL,     -- SERVICE=服务协议
                                                    -- DATA_PROCESS=数据处理协议
                                                    -- PRIVACY_NOTICE=隐私告知
                                                    -- VALUE_ADDED=增值服务授权
    version_no          VARCHAR(20)   NOT NULL,     -- 版本号: V1.0, V1.1, V2.0
    version_title       NVARCHAR(200) NOT NULL,     -- 版本标题
    effective_date      DATETIME      NOT NULL,     -- 生效日期
    
    -- ═══ OSS存储 ═══
    oss_bucket          VARCHAR(100)  NULL,         -- OSS Bucket名
    oss_key             VARCHAR(500)  NOT NULL,     -- OSS对象Key
                                                    -- 格式: agreements/{type}/{version}/agreement.pdf
    oss_url             NVARCHAR(1000) NULL,        -- OSS访问URL(签名URL或公开URL)
    content_hash        VARCHAR(64)   NOT NULL,     -- 文件SHA256哈希(防篡改)
    
    -- ═══ 变更说明 ═══
    change_summary      NVARCHAR(2000) NULL,        -- 本版本变更摘要
    prev_version_id     BIGINT        NULL,         -- 上一版本ID
    
    -- ═══ 状态 ═══
    is_current          BIT           NOT NULL DEFAULT 0,  -- 是否当前生效版本
    is_published        BIT           NOT NULL DEFAULT 0,  -- 是否已发布
    
    created_by          VARCHAR(50)   NULL,
    created_time        DATETIME      NOT NULL DEFAULT GETDATE(),
    
    CONSTRAINT UK_agreement_version UNIQUE (agreement_type, version_no)
);

-- 企业签署记录(企业管理员签署)
CREATE TABLE sys_agreement_sign (
    sign_id             BIGINT IDENTITY(1,1) PRIMARY KEY,
    
    -- ═══ 签署主体 ═══
    enterprise_id       BIGINT        NOT NULL,     -- 企业ID
    enterprise_name     NVARCHAR(200) NOT NULL,     -- 企业名称
    signer_user_id      VARCHAR(50)   NOT NULL,     -- 签署人用户ID(企业管理员)
    signer_name         NVARCHAR(50)  NOT NULL,     -- 签署人姓名
    signer_role         VARCHAR(30)   NOT NULL,     -- 签署人角色(ENTERPRISE_ADMIN)
    
    -- ═══ 签署的协议版本 ═══
    version_id          BIGINT        NOT NULL,     -- 签署的协议版本
    agreement_type      VARCHAR(30)   NOT NULL,     -- 协议类型
    version_no          VARCHAR(20)   NOT NULL,     -- 协议版本号
    
    -- ═══ 授权范围(数据处理协议特有) ═══
    auth_algo_training  BIT           NOT NULL DEFAULT 0,  -- 授权算法训练
    auth_region_index   BIT           NOT NULL DEFAULT 0,  -- 授权区域指数
    auth_benchmark      BIT           NOT NULL DEFAULT 0,  -- 授权行业基准
    auth_supply_match   BIT           NOT NULL DEFAULT 0,  -- 授权供需匹配
    auth_price_analysis BIT           NOT NULL DEFAULT 0,  -- 授权行情分析
    auth_product_improve BIT          NOT NULL DEFAULT 1,  -- 授权产品改进(默认开)
    auth_customer_success BIT         NOT NULL DEFAULT 1,  -- 授权客户成功(默认开)
    
    -- ═══ 签署信息 ═══
    sign_time           DATETIME      NOT NULL,     -- 签署时间
    sign_ip             VARCHAR(50)   NULL,         -- 签署IP
    sign_device         VARCHAR(200)  NULL,         -- 签署设备信息
    
    -- ═══ OSS存档(签署快照) ═══
    sign_snapshot_oss_key VARCHAR(500) NULL,         -- 签署时协议快照的OSS Key
                                                    -- 格式: signs/{enterpriseId}/{type}/{version}/{timestamp}.pdf
    
    -- ═══ 状态 ═══
    sign_status         VARCHAR(10)   NOT NULL DEFAULT 'ACTIVE',
                                                    -- ACTIVE=有效 SUPERSEDED=已被新版替代 REVOKED=已撤回
    superseded_by       BIGINT        NULL,         -- 被哪条签署记录替代
    revoked_time        DATETIME      NULL,
    revoked_reason      NVARCHAR(500) NULL,
    
    CONSTRAINT FK_sign_version FOREIGN KEY (version_id)
        REFERENCES sys_agreement_version(version_id)
);

CREATE INDEX IX_sign_enterprise ON sys_agreement_sign(enterprise_id, agreement_type);
CREATE INDEX IX_sign_version ON sys_agreement_sign(version_id);

-- 用户知悉记录(普通用户阅读确认)
CREATE TABLE sys_user_acknowledgment (
    ack_id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    user_id             VARCHAR(50)   NOT NULL,
    user_name           NVARCHAR(50)  NULL,
    enterprise_id       BIGINT        NOT NULL,
    version_id          BIGINT        NOT NULL,     -- 知悉的隐私告知版本
    ack_time            DATETIME      NOT NULL,
    ack_ip              VARCHAR(50)   NULL,
    
    CONSTRAINT UK_user_ack UNIQUE (user_id, version_id)
);
```

### 2.2 协议版本变更触发重新确认流程

```
┌─────────────────────────────────────────────────────────────────┐
│  协议变更 → 重新确认流程                                         │
│                                                                 │
│  Step 1: 平台运营发布新版协议                                     │
│    · 上传新版协议PDF到OSS                                        │
│    · 创建 sys_agreement_version 记录                             │
│    · 设 is_current=true, 旧版 is_current=false                   │
│    · 填写 change_summary (变更摘要)                              │
│                                                                 │
│  Step 2: 系统自动检测                                            │
│    · 用户登录时, 检查: 该企业签署的版本 vs 当前生效版本            │
│    · 如果 企业签署的 version_id ≠ 当前 is_current 的 version_id   │
│    → 触发重新确认                                                │
│                                                                 │
│  Step 3: 区分角色处理                                            │
│                                                                 │
│    如果登录者是企业管理员:                                        │
│    ┌────────────────────────────────────────────────────┐       │
│    │  弹出全屏协议确认页面(不可跳过):                     │       │
│    │  · 显示变更摘要(高亮变更内容)                        │       │
│    │  · 显示完整协议(可滚动阅读)                          │       │
│    │  · 授权范围勾选(可调整)                              │       │
│    │  · 签署确认按钮                                      │       │
│    │  · 签署后: 创建新 sys_agreement_sign 记录             │       │
│    │    旧记录 sign_status → SUPERSEDED                   │       │
│    │    保存签署快照到OSS                                  │       │
│    └────────────────────────────────────────────────────┘       │
│                                                                 │
│    如果登录者是普通用户:                                          │
│    ┌────────────────────────────────────────────────────┐       │
│    │  检查: 该企业管理员是否已签署新版?                    │       │
│    │                                                    │       │
│    │  已签署 → 弹出简化知悉弹窗:                          │       │
│    │    "平台隐私政策已更新(V2.0), 贵企业管理员已确认。    │       │
│    │     主要变更: xxx。点击'我已知悉'继续使用。"          │       │
│    │    → 创建 sys_user_acknowledgment 记录               │       │
│    │                                                    │       │
│    │  未签署 → 提示等待:                                  │       │
│    │    "平台协议已更新, 请联系贵企业管理员[xxx]确认后      │       │
│    │     方可继续使用。"                                  │       │
│    │    → 阻止使用(只能看到此提示页面)                     │       │
│    └────────────────────────────────────────────────────┘       │
│                                                                 │
│  Step 4: OSS存档                                                │
│    · 每次签署都将当时版本的协议PDF保存一份到OSS                    │
│    · Key: signs/{enterpriseId}/{type}/{version}/{timestamp}.pdf  │
│    · 即使后续协议内容修改, 企业签署的那份永久保留                  │
│    · 保留content_hash用于验证完整性                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```
  ├── templates/                          # 协议模板(当前版本)

  └── signs/                             # 企业签署快照(永久保留)

      ├── ENT-002/                       # 企业B
      │   └── ...
      └── ...
```

## 5. 后端API设计

```
# ═══ 协议版本管理(平台运营) ═══
POST   /api/v1/agreement/version              # 创建新版协议(上传PDF到OSS)
GET    /api/v1/agreement/version/current       # 获取各类型当前生效版本
GET    /api/v1/agreement/version/{type}/history # 版本历史

# ═══ 企业签署(企业管理员) ═══
POST   /api/v1/agreement/sign                  # 企业管理员签署协议
GET    /api/v1/agreement/sign/check            # 检查当前企业是否需要重签
GET    /api/v1/agreement/sign/history           # 签署历史
GET    /api/v1/agreement/sign/{signId}/download # 下载签署存档(OSS)
PUT    /api/v1/agreement/auth-scope             # 修改授权范围(触发重签)

# ═══ 用户知悉(普通用户) ═══
POST   /api/v1/agreement/acknowledge           # 用户确认知悉
GET    /api/v1/agreement/acknowledge/check      # 检查是否需要知悉新版

# ═══ 授权查询(业务服务调用) ═══
GET    /api/v1/agreement/enterprise/{id}/scope  # 查询企业授权范围
       返回: { algoTraining: true, regionIndex: true, benchmark: false, ... }
```

```
  │                                                             │
  │  如果 needSign=false:                                       │
  │    → 正常进入系统                                           │
  └─────────────────────────────────────────────────────────────┘
```

## 7. 合规保障措施

```
┌──────────────────────────────────────────────────────────────────┐
│  合规保障                                                        │
│                                                                  │
│  1. 告知义务                                                     │
│     · 协议中明确列出所有数据使用场景                              │
│     · 新增使用场景 → 发布新版协议 → 触发重新确认                  │
│     · 不得在协议约定范围之外使用数据                              │
│                                                                  │
│  2. 最小必要原则                                                 │
│     · 只采集业务运行和约定场景所必需的数据                        │
│     · 行为数据不含业务数据内容(不记录合同金额等)                  │
│     · 聚合数据最少5家企业才生成(防止反推)                        │
│                                                                  │
│  3. 授权可撤回                                                   │
│     · 企业管理员可随时调整授权范围                                │
│     · 撤回授权后, 立即停止相关数据使用                            │
│     · 已用于训练的模型无法撤回, 但不再使用新数据                  │
│                                                                  │
│  4. 数据安全                                                     │
│     · 业务数据: 加密存储, 传输HTTPS                              │
│     · 聚合数据: 脱敏处理, 不可反推单个企业                       │
│     · OSS存档: 签署记录永久保留, 防篡改(content_hash)            │
│     · 数据出境: 不涉及(服务器在国内)                             │
│                                                                  │
│  5. 用户权利                                                     │
│     · 查询权: 企业管理员可查看所有签署记录和授权范围              │
│     · 更正权: 可联系平台更正错误数据                              │
│     · 删除权: 企业停用后可申请删除全部数据(保留30天后执行)        │
│     · 导出权: 企业可导出自己的全部业务数据                        │
│                                                                  │
│  6. 法律基础                                                     │
│     · 参考: 《中华人民共和国个人信息保护法》                      │
│     · 参考: 《中华人民共和国数据安全法》                          │
│     · 参考: 《网络数据安全管理条例》                              │
│     · 企业数据处理基于"合同必要"和"同意"双重基础                 │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```
